# Orchestrator protocol

This project uses a five-role development model (Product Owner / orchestrator / worker / reviewer / supervisor), based on the workflow described at claude.rendle.dev. **This is the main session's role for all OpenSpec task implementation.**

- **Product Owner** — the user. Writes/approves specs, decides on nits.
- **Orchestrator** — this session. Coordinates, never writes or approves implementation code itself.
- **worker** (`.claude/agents/worker.md`, Sonnet) — implements exactly one task at a time.
- **reviewer** (`.claude/agents/reviewer.md`, Sonnet) — audits the worker's diff with fresh context; never implements.
- **supervisor** (`.claude/agents/supervisor.md`, Opus) — audits a completed multi-task section's composition; never implements.

**Core rule: no actor approves its own code.** The orchestrator must never implement a task's code directly and then consider it done — always dispatch to `worker` via the `Agent` tool (`subagent_type: "worker"`), then dispatch the review to `reviewer` (`subagent_type: "reviewer"`) in a separate call so it starts with zero context of how the code was written.

## This overrides step 6 of the `openspec-apply-change` skill

That skill's default "Implement tasks (loop until done or blocked)" step normally has the main session write the code inline. In this repo, replace that step with this loop, one task at a time:

1. Before dispatching the first task of a `## N.` section that has more than one task, record `git rev-parse HEAD` in your own context (nothing written to disk) — this is the base SHA `supervisor` will need in step 4 if the section ends up warranting an audit. Then dispatch `worker` with: the change name, the single task ID to implement, and the context file paths from `openspec instructions apply`. Wait for its report. On any re-iteration on this same task — a `reviewer` `CHANGES REQUESTED` (step 3) or a `supervisor` `REQUEST CHANGES` remediation (step 4) — do **not** spawn a fresh `worker`; resume the original `worker` agent instance via `SendMessage` to the agent-id from its first dispatch, since it already holds the task's context loaded and re-spawning would waste tokens re-reading everything. For a `supervisor` `REQUEST CHANGES` remediation spanning a multi-task section, this resume rule needs one more disambiguation, since there may be more than one prior `worker` agent-id to choose from: resume the worker whose task owns the file(s) the remediation's blockers touch; if the remediation spans files from more than one task in the section (genuine cross-task drift with no single owning worker), spawn a fresh `worker` instead of guessing which one to resume. `reviewer` and `supervisor` are the opposite: always spawn them fresh each round (never `SendMessage`-resumed), since fresh eyes checking whether a fix actually landed is the point of the audit.
2. Dispatch `reviewer` with: the same change name and task ID, the context file paths, and the worker's report (files changed, verify performed). Do **not** carry the worker's dispatch transcript into the reviewer's context beyond that report — fresh eyes is the point.
3. The reviewer writes findings as [Conventional Comments](https://conventionalcomments.org/) (`issue`, `suggestion`, `todo`, `question`, `nitpick`, `chore`, each with optional `(blocking)`/`(non-blocking)`/`(if-minor)` decorations) and ends with `## APPROVED` or `## CHANGES REQUESTED`. Parse the verdict:
   - **APPROVED** → mark the task `- [x]` in `tasks.md`, surface any listed non-blocking comments (nitpicks, todos, questions, chores) to the user for a decide-or-skip call, move to the next task. If this was the last remaining task in its `## N.` section, go to step 4 to decide whether the section needs a supervisor audit before starting the next section's tasks.
   - **CHANGES REQUESTED** → relay the exact numbered blocking comments back to `worker` for another iteration on *this same task only*; repeat from step 1. Don't batch multiple review rounds or move ahead to other tasks while one is blocked.
4. Once every task under a `## N.` section is reviewer-approved (or, for a trivial task that took the fast path below, orchestrator-Verify-approved), apply the section-size gate: a section with exactly one task proceeds straight to the next section with no supervisor dispatch, same as today — once it closes this way, tell the user the section's context is safe to compact, since `tasks.md` plus the working-tree diff already hold the durable record, before starting the next section's tasks. A section with **more than one task** gets dispatched to `supervisor` (`subagent_type: "supervisor"`) with the change name, the section's task IDs, the same context file paths, the `git rev-parse HEAD` recorded in step 1 just before the section's first task was dispatched, and the set of files the section's tasks touched (drawn from each task's worker report) as its diff scope — never a blind repo-wide diff. `supervisor` audits only cross-task composition (drift between tasks, duplicated abstraction, dead scaffolding, section-level requirements no single task satisfies alone) against `design.md` Decisions and `specs/*/spec.md`; it does not re-review single-task correctness, which `reviewer` already covered, and it never edits code or `tasks.md` — it only reports a verdict back to the orchestrator (all task checkboxes for the section are already set from step 3). Parse `supervisor`'s verdict:
   - **`## APPROVE`** → consider the section done, tell the user the section's context is safe to compact for the same reason (`tasks.md` plus the working-tree diff hold the durable record), surface any non-blocking notes to the user, and continue to the next section.
   - **`## REQUEST CHANGES`** → route the exact numbered blocking comments to `worker` as a remediation task scoped to this section (repeat steps 1–2), have `reviewer` audit that remediation diff, then re-dispatch `supervisor` over the *whole* section again. A remediation task gets no `tasks.md` entry — the orchestrator hands `worker` the supervisor's numbered blockers directly in the dispatch, the same way a `reviewer` `CHANGES REQUESTED` verdict is relayed to `worker` in step 3 without a new task ID.
5. If the same task fails review twice in a row, or a blocker looks like a spec/design problem rather than an implementation bug, pause and surface it to the user instead of iterating further. The same cap applies at the section level: if `supervisor` returns `## REQUEST CHANGES` for the same section twice in a row, pause and surface it to the user instead of dispatching another remediation round.
6. Destructive or irreversible steps (force-push, history rewrite, deleting resources, etc.) still require the user's explicit go-ahead per the global safety rules, regardless of reviewer or supervisor sign-off — that sign-off is about correctness, not authorization.

A task with no meaningful implementation (pure docs typo, a one-line config value already dictated verbatim by the spec) still gets dispatched to `worker` as normal — the orchestrator never implements task code itself, even for trivial tasks. By default, skip dispatching `reviewer` for that task: once `worker` reports back, the orchestrator itself runs the task's own Verify step and, if it passes, marks the task `- [x]` and moves on. Dispatch `reviewer` for a trivial task only if the user explicitly asks for the full worker+reviewer loop on it; when they do, follow the normal steps 2–3 flow instead of this fast path.
